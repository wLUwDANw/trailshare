# TrailShare · 旅迹信物

> **一句话（给普通人）**：你和朋友互相推荐旅行地，但不想把原图和精确位置直接发出去。TrailShare 让你把一张照片的"类型偏好"（比如"自然风光，很喜欢"）装进一个**带火漆印的信封**发给朋友。朋友能验证"这确实是你寄的"，但**看不到原图、也打不开信封**——除非你把他设成收件人。他收下后，他的旅行助手以后推荐时能说："这是你从 A 那里学来的。"

**零后端 · 纯前端 · 文件传递 · 一切算法可单测。**

## 1. 30 秒跑起来

### 最快方式：双击启动

| 系统 | 双击这个文件 |
|---|---|
| Windows | `start.bat` |
| macOS | `start.command`（首次使用需在终端里跑一次 `chmod +x start.command`） |
| Linux | `start.sh`（首次使用需 `chmod +x start.sh`） |

脚本会自动检查 Node.js、自动安装依赖、启动服务器、打开浏览器。**第一次运行会装依赖，约 1–2 分钟；以后双击秒开。**

> 首次运行时 Windows 可能提示"Windows 已保护你的电脑"，点「更多信息」→「仍要运行」即可。

如果你更喜欢命令行，下面是原来的手动方式：

```bash
npm install
npm run dev      # http://localhost:5173
npm test         # 204 个用例
npm run exp      # 一次跑完 E1–E4，输出 Markdown 表
```

### 别人拿到这个仓库怎么跑

> **v2026.4 不兼容 v2026.3**：旧 `.trailshare` 会被拒绝，提示"此信物为旧版本，请让发送方重新生成"。

2. `npm install`
3. `npm run dev`
4. 浏览器打开 `http://localhost:5173/`

### 旅程与好友怎么调（v2026.4）

**最短验证路径（两个窗口）**

```text
1. 窗口 A：「旅程」→ 新建 → 加一天 → 加地点（名称/标签/星星/照片/配文）→ 再加一天
2. 窗口 A：「好友」页复制自己的公钥；窗口 B 打开应用，把它的公钥粘到 A 的「添加好友」
3. 窗口 A：「生成信物」→ 选这趟旅程 → 在时间线里取消勾选第二天 → 接收方只勾 B → 生成
4. 窗口 B：「导入信物」→ 只看到第一天的连续时间线，页面没有任何"共 N 天/处/组"
5. 窗口 B：接受 → 「记忆库」→ 给某张照片点星星（再点同一颗可取消）
6. 窗口 A：导入同一个文件 → 「不是给你的」（因为 A 没勾自己）
```

**常见现象对照**

| 现象 | 是不是 bug | 原因 |
|---|---|---|
| 导入页只显示部分天 | 正常 | 没勾的那些天**根本没打包**，界面上连"存在"都不暴露 |
| 显示「不是给你的」 | 正常 | 你没被任何一组勾选。换到发送方勾过的窗口 |
| 生成时提示"没有可见内容" | 正常 | 这一组把整天/整个地点都取消了勾选，包里会空 |
| 一个地点照片全被取消勾选 | 正常 | 这个地点不会打包（没有照片的地点没有展示意义） |
| 同一文件再导入显示"已接受这段旅程" | 正常 | 每个地点一条确定性边 ID，能精确判重 |
| 评星后推荐变了 | 正常 | 平均分 < 3 的记忆，其溯源边在喂给 fuse 前被按 rejected 处理 |

**想从零再来一遍**：DevTools → Application → Storage → **Clear site data**。这会同时清掉身份、旅程、记忆、评星、好友与链。

## 2. 它做什么、不做什么

### 做

- 把一段旅程（多天、多地点、每张图带配文）加密成信物 `.trailshare`，按人按组定向发送。
- 接收方可以验证：**来源**（Ed25519 签名，发件人抵赖不了）、**完整性**（改一字节就验签失败）、**承诺一致性**。
- 不是收件人时，连一组都解不开，只会看到"此信物不包含给你的内容"。
- 接受后进入本地记忆库，Agent 推荐时能引用来源，并且能**自动检验**这条引用是不是编的。

### 不做（每条都有理由）

| 不做 | 理由 |
|---|---|
| 原图云备份 | 隐私底线，照片永不离开设备 |
| 实时社交 / IM | 文件传递足够，避免搭服务器 |
| 公链主网部署 | 链是可选锚定，不是核心贡献 |
| 完整零知识证明 | 签名 + 承诺覆盖 90% 可验证需求，ZK 列为 Future Work |
| 接入 LLM（决策层） | 当前 LLM 只做查询解析和回答润色，不参与推荐排序与来源选择；决策仍由规则 Agent 完成（见第 8 节） |
| 联邦学习 | 参与者规模只有几十人，不满足联邦学习前提 |

## 3. 术语速查（小白友好）

| 术语 | 技术含义 | 通俗类比 |
|---|---|---|
| **语义偏好** | 不是"我喜欢龙门石窟"，而是"我喜欢人文历史类景点" | 不是说"我喜欢红烧肉"，而是说"我喜欢甜口的" |
| **信物** | 一个加密文件，含"加密照片 + 加密语义 + 可验证承诺" | 一封加了锁的信 |
| **承诺** | 对一段数据的哈希指纹，能验证"没变"，但不能反推内容 | 把指纹按在信封蜡上，但指纹不可逆推成"手" |
| **签名** | 用私钥盖章，任何人可用公钥验证"是某人盖的" | 火漆印：盖了章的信，谁都能用印章拓印核对 |
| **Ed25519** | 一种签名算法，密钥短、速度快 | 一种高级火漆印章 |
| **AES-GCM** | 对称加密，自带完整性校验 | 一把锁：同款钥匙才能开，改一个焊点盒子就报废 |
| **PBKDF2** | 把弱口令反复哈希成强密钥 | 把淡盐水反复蒸馏浓缩成盐 |
| **盐（salt）** | 随机数，防止相同口令产生相同密文 | 做菜加的"引子"：原料一样，每次味道也不同 |
| **哈希链** | 每条记录的哈希包含上一条的哈希 | 一条铁链，断一环全链断 |
| **溯源边** | 记录"这条记忆来自谁、何时、签名是什么" | 书里的"来源注释"：这个观点引自哪本书 |
| **反事实** | "如果这件事没发生，结果会怎样" | "如果 A 没推荐过这家店，你还会去吗" |
| **反事实忠实度** | 移除来源后推荐改变的比例 | 把 A 的推荐拿掉，推荐**真的变了**，说明 Agent 没瞎说 |
| **时间衰减** | 越老的记忆权重越低 | 三年前去的地方，对今天影响比上个月小 |
| **k-匿名** | 至少 k 个来源支持才算共识 | 十个人都说好才算"大家都好" |
| **OTS** | 把哈希锚定到比特币，证明"某时刻已存在" | 把信件的哈希登报公告 |
| **零知识证明** | 证明"我知道秘密"而不泄露秘密 | "我能证明我知道密码，但我不说"——本项目**不实现** |
| **联邦学习** | 各方本地训练，只上传梯度 | 各自在家练字，只交流经验，不交换字帖——本项目**不是** |

## 4. 科研四问与四个实验

四个实验都是纯函数 + 构造数据，`npx tsx` 可直接跑，输出 Markdown 表可粘进报告。

### 科研问题

| # | 问题 | 对应实验 |
|---|---|---|
| 1 | 在"看不到原图、看不到精确强度"的前提下，一条语义信物能被验证到什么程度？ | E1 |
| 2 | 当个人记忆与多个朋友信物冲突时，Agent 应如何融合并解释？ | E3 |
| 3 | Agent 说"这条偏好来自 A"时，这句话的反事实忠实度是多少？ | E2 |
| 4 | A→B→C 的多跳传播中，影响每跳衰减多少？ | E4 |

### E1 · 隐私–可验证–效用矩阵

```
| 粒度 | 隐私分 | 可验证分 | 效用分 | 说明 |
|---|---|---|---|---|
| 明文 (plain) | 0.000 | 1.00 | 1.00 | 照片与语义明文可读；签名/承诺均可验 |
| 加密 (encrypted) | 0.833 | 1.00 | 1.00 | 无口令只看到密文；侧信道（文件大小、创建时间）仍泄露少量信息 |
| 仅承诺 (commitment_only) | 0.983 | 0.60 | 0.20 | 连密文都不发；只能验签，承诺无法与内容比对，故可验证分下调 |

> 简化威胁模型：18 种 (tag, intensity) 组合均匀猜测，模拟 20000 次/组合，
> 实测猜对率 5.58%（理论值 5.56%）。
```

隐私分是一个**明确定义在代码里的模型**（`W_CONTENT=0.4, W_GUESS=0.3, W_LEAK=0.3`），不是领域公认指标。改权重会改数值，所以权重写在 `e1_privacy.ts` 的常量里，谁都能复算、能质疑。

### E2 · 反事实忠实度

```
| 问题 | 引用边数 | 移除前 top-3 | 移除后 top-3 | 翻转 |
|---|---|---|---|---|
| 为什么推荐人文历史？ | 2 | nature, heritage, food | nature, food, metropolis | ✓ |
| 为什么推荐自然风光？ | 2 | nature, heritage, food | heritage, food, metropolis | ✓ |
| 为什么推荐水乡古镇？ | 1 | nature, heritage, food | nature, heritage, food | ✗ |
| 为什么推荐都市风光？ | 2 | nature, heritage, food | heritage, food, metropolis | ✓ |
| 为什么推荐美食探索？ | 1 | nature, heritage, food | nature, heritage, metropolis | ✓ |
| 为什么推荐休闲度假？ | 1 | nature, heritage, food | nature, food, heritage | ✓ |

总解释数: 6
可检验解释数: 6（无引用边、无从反事实检验的 0 条已排除）
忠实解释数: 5
平均忠实度: 0.833
```

**报告里可以这么写**：溯源解释的平均反事实忠实度为 83.3%，即移除 Agent 引用的来源边后，83.3% 的推荐结果发生了改变。

**但必须同时写局限**：唯一那条不忠实的解释（水乡古镇）恰好是被解释标签本来就不在 top-3 的情况。这说明单边必要性检验会低估解释质量——当个人记忆已经主导时，移除某条社会边不会翻转推荐，解释会被判 0 分，但它其实是"部分真实"的。这是指标的已知边界，不是实现 bug。

### E3 · 三策略消融

**E3-a 主场景（自然分布）**

```
| 目的地 | A 简单投票 | B 信任加权 | C 验证加权 | 结果是否变化 |
|---|---|---|---|---|
| 人文历史 | 都市风光 | 都市风光 | 都市风光 | 否 |
| 自然风光 | 都市风光 | 都市风光 | 都市风光 | 否 |
| 水乡古镇 | 都市风光 | 都市风光 | 都市风光 | 否 |
| 都市风光 | 自然风光 | 美食探索 | 美食探索 | 是 |
| 美食探索 | 都市风光 | 都市风光 | 都市风光 | 否 |
| 休闲度假 | 都市风光 | 都市风光 | 都市风光 | 否 |

共 6 个目的地，1 个在三种策略下 top-1 不同。
```

**E3-b 贴身竞争场景（两条边权重差 12%，一验一未验）**

```
| 目的地 | A 简单投票 | B 信任加权 | C 验证加权 | 结果是否变化 |
|---|---|---|---|---|
| 人文历史 | 自然风光 | 自然风光 | 自然风光 | 否 |
| 自然风光 | 人文历史 | 人文历史 | 人文历史 | 否 |
| 水乡古镇 | 人文历史 | 人文历史 | 自然风光 | 是 |
| 都市风光 | 人文历史 | 人文历史 | 自然风光 | 是 |
| 美食探索 | 人文历史 | 人文历史 | 自然风光 | 是 |
| 休闲度假 | 人文历史 | 人文历史 | 自然风光 | 是 |

共 6 个目的地，4 个在三种策略下 top-1 不同。
```

**这是一组负结果 + 一组正结果，必须一起报**：

- 验证加成**不是万能药**。它把所有已验证边同比例放大，在自然分布下排名通常不动（1/6）。
- 只有当两条证据权重接近时，它才会翻盘（4/6）。
- 结论应该写成"可验证性在近身竞争时改变决策"，而不是"可验证性提升推荐质量"。

### E4 · 多跳传播衰减

```
| 跳数 | 路径 | 单跳权重 | 累积权重 | 直接份额 | 间接份额 |
|---|---|---|---|---|---|
| 1 | A→B | 0.514 | 0.514 | 100.0% | 0.0% |
| 2 | B→C | 0.539 | 0.277 | 48.2% | 51.8% |
```

## 6. 协议：一个信物是怎么封起来、又怎么验开的

> v2026.4 起，一个信物装的是**一段旅程的可见切片**：多天、多地点、每张图可带配文。
> 仍然是定向加密：只有被 wrap 过的收件人能解开。

### 封（A 侧，`src/share/pack.ts`）

```
每组：
1  过滤       applyVisibility(trip, visibility) → 可见 place + 可见 photo + 是否带配文
             没有可见 place → 抛"这组没有任何可见内容"
2  组密钥     key = random(32)
3  加密 meta  AES-GCM(key, ivMeta, { name, label?, date })     ← 地点名/日期/时段在密文里
4  加密照片   AES-GCM(key, ivPhoto, photo)                      ← 每张独立 IV
             有配文且未被屏蔽：AES-GCM(key, ivCaption, caption)
5  封钥匙     对每个接收方：临时 X25519 → ECDH → HKDF → 包一份组密钥
6  承诺       SHA256( 按 groupId 排序的 groupId||salt||(按 placeId 排序的 placeId||tag||intensity) )
7  签名       Ed25519.sign(canonical_json(body))                覆盖 groups + commitment + chain
8  打包       JSON → .trailshare
```

**承诺覆盖什么、不覆盖什么**

| 进承诺 | 不进承诺（在密文里） |
|---|---|
| 每个可见 place 的 `(placeId, tag, intensity)` + 每组 `salt` | 日期、地点名、`label`、配文、照片本身 |

为什么这样切：不持钥的人也能验证"这个组里有几个地点、标签分别是什么"，但看不到你去了哪、哪天去的。被屏蔽的 place 不打包，所以承诺也覆盖不到——**屏蔽与承诺天然一致**。

### 验（B 侧，`src/share/unpack.ts`）

```
0  版本闸门   只认 ts-2026.4，旧版本抛"此信物为旧版本，请让发送方重新生成"
1  结构校验   groups[].payload.places[].photos[]
2  验签       Ed25519.verify
3  承诺比对   只用公开字段复算
4  链锚       能查则查，查不到不算失败（三态）
5  逐组解封   解不开的组整组消失；解开的组里逐个 place 解 meta、照片、配文
              一组都解不开 → 抛"此信物不包含给你的内容"
```

### 包结构（v2026.4）

```jsonc
{
  "version": "ts-2026.4",
  "shareId": "s_xxxxxxxx",
  "from": { "displayName": "A", "pubkey": "ed25519:…", "sig": "ed25519:…" },
  "groups": [{
    "groupId": "g1_ab12cd",
    "payload": {
      "cipher": "aes-gcm",
      "salt": "…",
      "places": [{
        "placeId": "p_ab12cd",
        "tag": "nature",              // 明文：承诺要能被不持钥的人验证
        "intensity": "high",          // 明文：同上
        "ivMeta": "…",
        "encryptedMeta": "…",          // 密文：{ name, label?, date }
        "photos": [{
          "photoId": "ph_ab12cd",
          "encrypted": "…", "iv": "…",
          "encryptedCaption": "…", "ivCaption": "…"   // 被屏蔽时这两个字段不存在
        }]
      }]
    },
    "wrappedKeys": [{ "recipientPubkey": "…", "ephemeralPubkey": "…", "encryptedKey": "…", "iv": "…" }]
  }],
  "commitment": { "hash": "sha256:…", "algo": "sha256" },
  "chain": { "prevHash": "…", "seq": 0, "anchor": null },
  "createdAt": "2026-10-21T…"
}
```

**隐私边界（必须知道）**

| 明文 | 密文 |
|---|---|
| `tag` / `intensity`（承诺可验证的代价） | 日期、地点名、时段、配文、照片 |
| `groupId` / `placeId` / `photoId`（随机 ID，不含语义） | — |

## 7. 算法：融合、反事实、多跳

### 融合（`src/agent/fuse.ts`）

```
score(tag) = self(tag) + social(tag)

self(tag)   = Σ decay(daysSince(takenAt))
social(tag) = Σ w(edge)        ← 三种策略只在这里分叉
```

| 策略 | `w(edge)` | 用途 |
|---|---|---|
| `voting` | `1` | 基线：每个朋友一票 |
| `trust` | `trust(from) × decay(daysSince(acceptedAt))` | 老朋友、新分享权重更高 |
| `verified` | `trust × decay × (verified ? 1.2 : 1)` | 主策略：可验证性折算成可信度 |

- `trust(x) = accepted / (accepted + rejected + 1)`，分母 +1 让新朋友初始信任为 0。
- 有过拒绝记录的发件人，在 `trust` / `verified` 里再乘一次 `1 - 0.3 × 拒绝率`：骗过一次的代价高于少接受过一次。
- 时间衰减 `decay(d, h) = 0.5^(d/h)`，默认半衰期 90 天。
- 输出同时带 `contributions`，把每个 tag 的得分拆成"自己"和"每位朋友"，explain 和 UI 都直接用它。

### 反事实（`src/agent/counterfactual.ts`）

```
before = rank(全标签, 完整输入)
after  = rank(全标签, 移除解释引用的边)
flipped = before ≠ after
```

**这里和方案原文有一处刻意不同**：方案用 `recommend(explanation.tag, ...)`，而 `recommend` 会把"被解释的标签"当成目的地排除掉。那样被解释标签自己的分数永远不参与比较，指标会失真。所以反事实改用 `rankTags()`（不排除任何标签）。详见第 9 节。

### 多跳（`src/agent/multihop.ts`）

```
单跳权重 w  = trust × decay × (verified ? 1.2 : 1)
累积权重    = Π w
直接份额    = |log w_d| / Σ_{i≤d} |log w_i|
```

直接份额用**对数贡献分摊**，而不是简单的权重占比：这样它严格可加，且随链变长单调下降（间接份额单调上升），不会被"上游累积变小"这种伪影干扰。它是启发式归因，不是因果分解。

## 8. LLM 分层设计（MD-2）

> **一句话**：LLM 只负责"听懂问题"和"把话说顺"，**推荐排序和来源引用一条都不许它碰**。

### 8.1 谁决定什么

| 环节 | 由谁决定 | LLM 的权限 |
|---|---|---|
| 推荐排序 | `fuse()` + `rankTags()` | **禁止参与** |
| 引用哪几条来源边 | `explain()` 的规则逻辑 | **不能新增，也不能删除** |
| 问题解析（tag / 时间 / 关键词） | `query_parse_llm.ts` | 只能填槽位，字段越界即丢弃 |
| 回答措辞 | `llm_paraphrase.ts` | 只能换说法，`[gift:s_xxx]` 必须原样保留 |
| 引用一致性 | `self_check.ts` | **纯代码校验，LLM 不参与** |
| 反事实检验 | `counterfactual.ts` | **对象是规则 Agent 的排序结果，不是 LLM 文本** |

一句话记法：**LLM 是编辑，不是记者，更不是主编。** 它不能决定报什么，只能决定怎么说。

### 8.2 调用链

```
用户提问
  │
  ├─ parseQuery()            有 .env → LLM 解析；失败 → extractTag() 关键词兜底
  │
  ├─ buildExplanation()      规则产出 ruleAnswer + citedEdgeIds（决策都在这里）
  │
  ├─ LLM 未配置 ──────────────────────────────→ 返回 ruleAnswer
  │
  ├─ paraphrase()            只改表达
  ├─ selfCheck()             引用编号比对（多/少/编造 三类）
  │     ├─ 通过 ────────────────────────────→ 返回润色稿
  │     └─ 不过 → 重试一次
  │            └─ 仍不过 ───────────────────→ 返回 ruleAnswer + UI 标"规则版回答"
  │
  └─ faithfulness()          反事实检验永远跑在规则结果上，与 LLM 无关
```

### 8.3 三个新模块

| 文件 | 职责 | 关键约束 |
|---|---|---|
| `src/agent/llm_client.ts` | OpenAI 兼容的 `chat()`，10s 超时、失败重试 1 次、连续失败熔断 60s | 不认 tag、不认来源边，只收发文本 |
| `src/agent/query_parse_llm.ts` | 问题 → `{tag, timeRange?, keywords}` | 输出必须合法；`tag` 不是六类之一就置 `null`；解析失败退回关键词 |
| `src/agent/llm_paraphrase.ts` | 规则回答 → 润色稿 | system prompt 四条硬约束：不加引用、不删引用、不改编号、不编事实 |
| `src/agent/self_check.ts` | 润色稿的引用一致性校验 | 纯函数，多引 / 漏引 / 编造 / 空输出 / JSON 输出全部拦截 |

### 8.4 self_check 到底拦了什么

| 情况 | 结果 | 返回字段 |
|---|---|---|
| 引用集合完全一致 | 通过 | 三个数组都为空 |
| 多引用了一条真实存在的边 | 拦截 | `extraIds` |
| 漏引用了规则引用过的边 | 拦截 | `missingIds` |
| 引用了库里根本不存在的编号 | 拦截 | `fakeIds` |
| 输出里一个 `[gift:]` 都没有 | 拦截 | `missingIds` 全量 |
| 输出是 JSON / 代码块 / 空串 | 拦截 | `reason` 说明格式问题 |

ID 口径：回答里出现的是 `shareId`（`s_xxx`），而 `citedEdgeIds` 是内部边 ID（`e_xxx`），校验时统一折算成 `shareId` 再比，避免同一来源两种写法被误判。

## 9. 定向加密与传播边界（MD-3）

### 9.1 一句话

**一个文件里可以装多组内容，每组只对指定的人可见。** 转发给第三方，第三方打开只会看到"此信物不包含给你的内容"。

### 9.2 为什么是 KEM + DEM

| 步骤 | 做什么 | 为什么 |
|---|---|---|
| DEM | 每组一把随机 32 字节组密钥，AES-GCM 加密照片与 meta | 对称加密快，GCM 自带完整性 |
| KEM | 用接收方的 X25519 公钥 + 临时密钥做 ECDH，把组密钥单独包一份 | 不用为每个人存一把长期密钥，临时密钥用完即弃 |
| 绑定 | HKDF 的盐 = `sha256(临时公钥 ‖ 接收方X25519公钥)` | 防止同一把 wrapKey 在不同人之间复用 |
| 解封 | 逐个试 `wrappedKeys`，AES-GCM 解不开就是"不是给你的" | 不区分"密钥错"和"数据坏"，避免探测 |

Ed25519 → X25519 用的是 RFC 7748 的标准转换（`clamp(SHA512(seed)[0..32])`），所以**老用户的种子不用换**，X25519 密钥每次从种子里重新派生。

### 9.3 传播边界（必须写进报告）

> **传播边界 = 文件级定向，不是内容级不可转发。**

| 能防住 | 防不住 |
|---|---|
| 文件被转发给未授权的人，他打不开（连"有几组、是什么标签"都看不到） | 授权用户解密后截图 |
| 多组并行，A 只看得到组 1、B 只看得到组 2 | 授权用户解密后重新加密转发 |
| 中间人改任意一组 → 验签 + 承诺双失败 | 授权用户主动把内容念给别人听 |
| 旧版本信物被拒绝，不会被降级攻击 | 发送方自己泄露（他本来就有明文） |
| 界面不暴露组数与序号（但文件结构里仍可见，见下方说明） | — |
| 屏蔽的条目**根本不在包里**，接收方连占位都看不到 | 文件大小仍可能泄露"这次只有 2 天而不是 3 天" |
| 评星只存在本机，不随信物传递 | 对方看不到你的评价，也影响不到他的设备 |

这不是 DRM，是"信封"：**它保证信只能被收件人拆开，但拆开之后内容就不再受控。**

**必须知道的边界**：

1. **屏蔽 = 不打包，不是不可见**。被取消勾选的 Day/Place/Photo 完全不在包里，接收方看到的是连续时间线；但文件大小会随可见内容变化，理论上能猜出"这次带的天数不多"。
2. 导入界面不显示"共 N 天/处/组"，但 `.trailshare` 是 JSON，`cat` 一下仍能看到 `groups[]` 里有几个 place、每个的 `tag`。**真正的隐私保证是"打不开内容"，不是"看不到有几个地点"。**
3. **评星是本地数据**。它存在 `Memory.ratings` 里，不写进任何信物，也不会同步给对方。

### 9.4 三窗口演示（界面版）

**手工点（约 5 分钟）**

1. 三个互相隔离的窗口 A / B / C 各打开一次应用。
2. A 进「好友」页复制自己的公钥；B、C 也各自复制，粘到 A 的「添加好友」里。
3. A 建一趟两天旅程：Day 1「龙门石窟」、Day 2「老君山」，各带照片。
4. A 进「生成信物」：
   - 组 1：取消勾选 Day 2 → 接收方只勾 **B**
   - 「＋ 添加一组」会复制组 1 → 改回 Day 2、取消 Day 1 → 收件人改成 **C**
   - 生成 → 下载 `s_xxx.trailshare`
5. B 导入 → 时间线只有 Day 1 → 接受。
6. C 导入 → 时间线只有 Day 2。
7. 再开一个没被勾选的窗口 D → 导入同一个文件 → 「不是给你的」。

覆盖同样场景的用例：`多组并行：B 只能解组 1，C 只能解组 2`、`未授权用户：抛「不包含给你的内容」`、`视图层不暴露组数（收尾要求）`。屏蔽本身由 `tests/filter.test.ts` 与 `tests/pack.test.ts` 守着（例如"屏蔽一整天 → 包结构里没有这一天的任何地点"）。

### 9.6 版本迁移

| 版本 | 格式 | 能否打开 |
|---|---|---|
| `ts-2026.2`（含更早） | 单组 + 口令 | **不能**。导入时直接报"此信物为旧版本，请让发送方重新生成" |
| `ts-2026.3` | 多组 + 单地点 + 照片组 | **不能**。没有 place 概念，语义对不上 |
| `ts-2026.4` | 多组 + 多地点时间线 + 评星 | 当前版本 |

没有做兼容层：v2026.3 的一个 group 只有一个 tag，v2026.4 的一个 group 是一串地点；硬转只能把整组压成一个地点，会把时间线弄丢。

## 10. 好友与公钥交换

### 10.1 三条路，按场景选

| 场景 | 怎么做 | 代码 |
|---|---|---|
| 本地演示 | 首次启动自动塞 3 个 `[测试]好友A/B/C` | `seedDemoFriends()`（幂等） |
| 真实使用 | 让对方把公钥发给你，粘进「好友」页 | `addFriend()` |
| 换设备 | 没有导出/导入身份的 UI，**换设备等于换身份** | 见 13 节局限 |

### 10.2 手工加好友的三步

1. 对方打开「好友」页 → 点「复制公钥」，得到 `ed25519:<64 位 hex>`。
2. 你打开「好友」页 → 粘进"对方的公钥" → 填一个备注名 → 添加。
3. 回到「生成信物」，他就会出现在每组的"接收方"列表里。

X25519 公钥不用对方提供：从 Ed25519 公钥用 RFC 7748 的标准转换派生，两边算出来一定一样（`src/crypto/keys.ts` 的 `ed25519ToX25519Pub`）。

### 10.3 内置测试好友是什么

`seedDemoFriends()` 在好友表为空时插入 3 个固定种子的身份（`11…` / `22…` / `33…`）。**它们的私钥就写在仓库里**（`src/store/friends.ts`），所以：

- 用途只有一个：让"三窗口演示"和你自己的脚本可复现；
- 名字带 `[测试]` 前缀，看到就知道不是真人；
- 绝不能拿它们做真实分享——任何人都能解开寄给它们的信物。

### 10.4 为什么不做实时加好友协议

实时加好友需要在线状态、密钥目录、身份验证、防中间人，任何一项都要求后端或至少一个可信第三方。这和"零后端、文件传递"的前提冲突。当前的选择是：**公钥交换走带外渠道（微信/邮件/当面），TrailShare 只负责"拿到公钥之后"的部分。**

### 10.5 一个必须知道的风险

**公钥没有验证机制。** 你复制到的 `ed25519:…` 如果被人替换，你会把照片加密给错误的人，而且签名、承诺、链全都"验证通过"——因为它们只保证"内容与这把公钥一致"，不保证"这把公钥是谁"。

生产环境需要带外核验：比对公钥指纹（前 8 位不够，至少 16 位）、扫二维码、或者当面确认。这一条已列进 13 节局限。

**必须遵守的边界**（违反了 vitest 会在 Node 环境挂）：

- 决策相关的模块——`fuse.ts`、`recommend.ts`、`explain()`、`counterfactual.ts`、`multihop.ts`、`crypto/commitment.ts`、`crypto/chain.ts`、`utils/time.ts`、`utils/trust.ts`——**不访问 IndexedDB、不调用 `crypto.subtle`、不读 `Date.now()`、不联网**。时间一律作为 `now: Date` 传进来。
- MD-2 新增的 `llm_client.ts` / `query_parse_llm.ts` / `llm_paraphrase.ts` 会发网络请求，但**不参与任何决策**，且全部带降级路径：网络失败、超时、JSON 不合法、引用不一致，最终都回到规则版回答。`self_check.ts` 是纯函数，不联网。
- `crypto/encrypt.ts`、`crypto/sign.ts`、`crypto/keys.ts` 可以内部用 WebCrypto，但对外只收发 `Uint8Array` / `string`。
- `store/*` 只做 CRUD + `ArrayBuffer` 转换，不含算法。
- `share/*` 是 Crypto 的组合调用，不碰数据库。

**两个工程细节**：

1. **IndexedDB 一律存 `ArrayBuffer`**。Safari 存 `Uint8Array` 可能读回 `ArrayBuffer`，某些 inline-key 场景直接抛错。所有读写都过 `toStorage` / `fromStorage`。
2. **签名格式统一带前缀**（`ed25519:` / `sha256:`），尽管现在只有一个算法——这样将来加算法时旧包还能解析。

## 12. 与方案文档的差异（诚实清单）

按方案实现时，有 34 处做了偏离或补充。每一处都在下面说明"为什么"，因为**隐瞒差异比差异本身更糟**。

| # | 差异 | 原因 |
|---|---|---|
| 1 | `plain` 档新增 `payload.plainPhotos` / `payload.plainMeta` 字段 | 方案 7.1 的 schema 里没有放明文的位置，但 6.5 又要求明文档能直接看照片和语义。只能扩字段。 |
| 2 | 反事实用 `rankTags()` 而非 `recommend(tag)` | 方案 9.3 的代码会把被解释标签排除出推荐列表，导致该标签自己的分数不参与比较，"拿掉来源后是否翻转"几乎永远判否。这是个会让指标失真的 bug，已修。 |
| 3 | `commitment_only` 的可验证分从 1.0 下调到 0.6 | 方案预期表给 1.0，但该档没有内容，承诺**无法与内容比对**，只能验证"签名覆盖了这个哈希"。诚实起见下调。 |
| 4 | E1 隐私分是三项加权模型 | 方案只给了"猜对概率"一个维度，无法解释"加密档 0.9 / 仅承诺 1.0"的差别。改成 `0.4×内容隐藏 + 0.3×(1−猜对率) + 0.3×(1−侧信道泄露)`，权重写在代码常量里。 |
| 5 | E3 增加"贴身竞争"场景 | 主场景下验证加权不改变任何排名（负结果）。只报负结果会让人误以为实现有问题，只报正结果则是挑数据。两个都报。 |
| 6 | E4 的份额用对数归因 | 方案给的示例表数字（0.35/0.65/0.77）不是任何公式的结果。用"权重占比"会随跳数非单调，只能用对数分摊才自洽。 |
| 7 | 链校验改成三态（true / false / null） | 跨设备根本看不到对方的链，"prevHash 存在于本地账本"多数时候无法成立。区分"验证通过"和"无法验证"比假装失败或假装通过都好。 |
| 8 | 未实现 OTS（L1） | 需要几小时等待 + 外部服务可用性，第 4 周时间不够。`chain.anchor` 恒为 `null`，接口留好。 |
| 9 | 新增"我的昵称"字段 | 方案把发件人写死为 `A`。演示时要两个窗口互发，昵称必须可填。**昵称可伪造，身份永远以公钥为准**，UI 里也这么写。 |
| 10 | 新增右上角"链锚定"开关 | 方案要求 `chain_enabled` 通过 localStorage 控制。做成可见开关，演示"关掉链也能用"时不用开控制台。 |
| 11 | devDependencies 多了 `tsx`、`@types/node` | 方案要求 `npx tsx src/experiments/eX.ts` 能直接跑。不装 tsx 就得联网现下。 |
| 12 | 多跳没有真实多用户实现 | E4 用构造的 A→B→C→D 链。真实多跳需要三个浏览器 profile 手传文件，演示成本过高，且不增加科学结论。 |
| 13 | MD-2 改了 `src/ui/tabLibrary.ts`（不在该轮白名单） | LLM 调用是异步的，而界面原来的 `renderAnswer()` 是同步的。不改这一个调用点，`explainWithLLM` 就没有任何入口，功能等于不存在。改动只有：`await explainWithLLM(...)` + 一个"规则版回答"角标。 |
| 14 | `explain()` 保持同步，另开 `explainWithLLM()` | `tests/counterfactual.test.ts` 与反事实检验都同步调用 `explain()`。把 `explain()` 改成 async 会连带破坏既有测试与"决策路径的纯函数性"。规则版与 LLM 版彻底分家，前者永远不受网络影响。 |
| 15 | `dotenv` 放在 devDependencies | `VITE_` 变量由 Vite 自己注入，dotenv 不是运行时依赖，放在 dependencies 会误导读者。 |
| 16 | LLM 输出是 JSON/代码块时直接判失败 | 方案只要求"编号一致"，但 JSON 包裹的文本即使编号对，也不能直接展示给用户。判失败更安全。 |
| 17 | 加了熔断（连续 2 次失败后 60s 快速失败） | 否则每次提问要等 10s 超时 × 重试 × 解析+润色两轮，最坏接近一分钟。熔断让"服务挂了"变成"立刻退回规则版"。 |
| 18 | `pack()` 入参从 `photos` 改成 `groups[]`，并加了 `packMultiGroup` 别名 | MD-3 要求一组对一批人。别名只是让多组场景读起来更清楚。 |
| 19 | 改了 `tabCreate.ts` / `tabImport.ts`（不在阶段 3 白名单） | pack/unpack 的 API 变了，不改这两个调用点 `tsc` 直接红、构建过不了。改动只到"能编译 + 能自收自发"的程度，完整多组 UI 放在阶段 4。 |
| 20 | 好友名单用独立 IndexedDB（`trailshare-friends`） | 主库 `src/store/db.ts` 不在白名单里，没法加 objectStore。好友本来就是"本机通讯录"，单独一个库反而更清晰。 |
| 21 | `wrapKeyForRecipients` / `unwrapKey` 返回 Promise | 签名要求同步返回，但 AES-GCM 走 WebCrypto 只能异步；KEM 那一半（X25519/HKDF）确实是同步的。 |
| 22 | `senderX25519Priv` 只做长度校验，不参与 KDF | `unwrapKey(wrapped, myPriv)` 拿不到发送方公钥，任何用到发送方私钥的派生对方都无法复现。机密性由临时 ECDH 保证；这个参数留给将来的认证 KEM。 |
| 23 | `tag` / `intensity` 在包里是明文 | 承诺必须能被"不持钥的人"验证，而承诺又要覆盖语义——只能把语义公开。这是隐私上的回退，已在 6 节与 12 节写明。 |
| 24 | 产品层去掉"明文 / 仅承诺"两档 | 定向加密的模型下，"谁能看"由 wrap 决定，口令与承诺档没有位置。E1 保留为模型级研究（数字不变）。 |
| 25 | 溯源边 ID 改成确定性写法 `e_<shareId>_<groupId>` | MD-4 要求"每组独立接受/拒绝"，但一组一落边就需要判重。`ProvenanceEdge` 没有 groupId 字段，而 `store/provenance.ts` 不在白名单——用确定性 ID 既不改 schema，又能精确识别"这一组是否处理过"。 |
| 26 | 多组 UI 额外保留"我自己（本机回看）"收件人 | MD-4 的草图只列好友。不勾自己，发送方自己都打不开导出的文件，演示和排错都会卡住。默认勾选，可以取消。 |
| 27 | 地点提示是"全局"的，不是每组一个 | MD-4 的草图里没有地点字段。为了不丢 Phase 1 的能力，保留一个输入框，应用于本次所有组；真要分组不同地点，生成两次。 |
| 28 | 导入页曾经显示组号（**已废弃**） | 早期版本写"给你的第 N 组"。包里可能共 3 组、解开的只有第 2 组，写"组 2"会让人以为只有一组能看。**分发前收尾已彻底删掉组号与组数**，见第 29 条。 |
| 29 | 另开 `unpackForViewer()`，没有改 `unpack()` 的返回结构 | 收尾要求"返回值改为 ok/groups 且不含总数"，但 `unpack()` 被 9 个测试文件和四个实验依赖（`report` / `meta` / `canAccept`），改它必然要改既有断言，而本轮禁止改现有测试。于是算法层接口保持原样，另加一个只回"解开的组 + 发件人"的视图函数，UI 只调后者——**UI 拿不到 pkg，也就拿不到组数**。 |
| 30 | `package.json` 的 `files` 里加了 `tests/`（MD 的清单没有） | 清单漏了 tests，但出口条件要求接收方 `npm test` 全绿；不带 tests 的包跑测试会"0 个文件通过"。另：npm 从不打包 `package-lock.json`，要完整锁版本请直接发仓库压缩包。 |
| 31 | 旅程与屏蔽用独立 IndexedDB（`trailshare-trips`） | `src/store/db.ts` 不在白名单，加不了 objectStore。旅程是编辑中的草稿，和记忆/边没有事务关联，独立小库反而更清楚（和 `friends.ts` 同样的处理）。 |
| 32 | 一个地点的照片全被屏蔽 → 这个地点不打包 | 没有照片的地点没有展示意义，强行打包会生成一张空地点卡。空地点也不会出现在承诺里，屏蔽与承诺保持一致。 |
| 33 | 溯源边按"地点"粒度落（一个地点一条） | `Memory` 是地点粒度（tag/intensity 挂在 place 上），而 `fuse` 通过 `edge.memoryId` 找记忆。按组落边会让一个组只能贡献一个 tag，时间线里其余地点就白收了。 |
| 34 | 评星用 `ratingAdapter` 把低分边标 `rejected`，不改 `fuse` | `fuse` 的输入是 edges，不是 counts。适配层在喂给 fuse 前做转换，既让差评生效，又保证 E1–E4 的输入完全不变。 |

### 方案里被验证成立的部分

- 三档粒度确实构成一条可量化的隐私–效用权衡曲线（E1：0.000/0.833/0.983 对 1.00/1.00/0.20）。
  **注意**：v2026.3 为了做定向加密，产品层只保留了"加密"这一档，E1 现在是一个模型级研究，不再是 UI 上的三个开关。
- 反事实忠实度确实可以全自动计算，不需要人工标注（E2：0.833）。
- 三策略确实能给出不同推荐，差异集中在近身竞争（E3-b：4/6）。
- 签名 + 承诺确实覆盖了"来源可验证 + 内容不可篡改 + 语义不可替换"，没有 ZK 也能自洽。

## 13. 局限与 Future Work

### 必须写进报告的局限

1. **链不是科研贡献**，是使能技术。四个实验才是贡献。
2. **不是联邦学习**。参与者规模只有几十人，做的是"本地计算 + 签名传递 + 逻辑聚合"。
3. **威胁模型是简化的**。E1 的攻击者是"均匀猜测 + 侧信道"的模型，不是真实攻击者，没有做流量分析、没有做照片指纹比对。
4. **样本量小**。E2/E3/E4 全部基于构造数据，结论适用于小规模场景。
5. **私钥以 hex 存 IndexedDB**。WebCrypto 路径下私钥是导入后即弃的，但降级到 `@noble/ed25519` 时种子明文落盘。生产环境必须改用不可导出的 `CryptoKey` 或加密存储。
6. **昵称不参与验证**。同一公钥可以自称任何名字，UI 只把公钥前 8 位当身份指纹。
7. **`commitment_only` 是单向的**。对方永远拿不到内容，这不是"暂时锁住"，是"永久没有"。UI 上必须说清楚。
8. **没有做密钥轮换与撤销**。身份一旦生成就固定。
9. **LLM 的 Key 在前端**。`VITE_` 变量会被打进产物，只适合本地/内网演示；生产必须走服务端代理（见 8.6）。
10. **`self_check` 只校验引用编号，不校验语义**。模型若把"强烈推荐"改写成"值得一去"能通过；若把"高"改成"中"，编号仍然一致，检测不到。要做语义保真，需要再加一层"档位/数字一致性"检查。
11. **润色只在有引用边时发生**。只引用自己照片、没有社会边的回答会直接走规则版，不做润色。
12. **没有缓存 LLM 结果**。同一个问题问两次就调用两次（会消耗额度）。
13. **传播边界是文件级**。定向加密防的是"文件被转发"，防不住"授权用户截图/重加密"。见 9.3。
14. **组语义是公开的**。`tag` / `intensity` / `coverIndex` 在包里明文，任何人都能看出"这个信物里有 2 组、分别是自然和人文"。这是承诺可验证的代价。
15. **没有前向安全的棘轮**。临时密钥保证"每次包装独立"，但没有 Double Ratchet 那种逐消息演进。
16. **好友公钥靠手工交换，没有验证机制**。你复制到的公钥如果被人替换，你会把内容加密给错误的人。生产环境需要带外核验（二维码/短指纹）。
17. **不兼容旧包**。v2026.2 及更早的 `.trailshare` 一律拒绝，没有迁移工具。
18. **身份不能导出/导入**。种子只在本机 IndexedDB 里，清站点数据或换设备就等于换身份，之前发给你的信物全部打不开。生产环境需要种子备份（助记词 / 二维码）。
19. **"拒绝某一组"的语义是粗粒度的**。每组各落一条拒绝边，trust 会把它们分别计数；如果发送方一次寄 3 组、你拒了 2 组，他的信任分会掉得比"只寄 1 组"更狠。这是有意为之（三次不受欢迎的推送），但需要知道。
20. **重装/清数据后无法识别"这一组已接受过"**。判重靠本地 edges 表里的确定性 ID，边被删掉（删记忆）之后，再导入同一个文件可以重新接受。
21. **文件大小与可见天数存在侧信道**。屏蔽 = 不打包，所以"只发了 2 天"会直接反映在包体积上；攻击者拿到文件能猜个大概，只是看不到具体内容。
22. **日期与地点名是强识别信息**。加密保护的是"传输过程"和"未授权的人"，不保护"收件人自己"——他本来就能看到你去了哪、哪天去的。
23. **评星只在本机生效**。它不会随信物回传，也不会同步到其他设备；换设备后评星丢失，信任分随之回到"未评 = 接受"。

## 14. 打包分发

```bash
# 生成可分发压缩包（不含 node_modules / dist / .env.local）
npm pack
# 得到 trailshare-0.1.0.tgz
```

接收方解压后：

```bash
tar -xzf trailshare-0.1.0.tgz
cd package
npm install
npm run dev
```

**打包前必做检查**

```bash
# 1. 确认没有真实 Key
grep -rn "sk-[a-zA-Z0-9]" --include="*.ts" --include="*.md" src/ README.md

# 2. 确认 .env.local 不在包里
tar -tzf trailshare-0.1.0.tgz | grep -c "node_modules"   # 应为 0

# 3. 确认测试全绿
npm test -- --no-file-parallelism
```

`package.json` 的 `files` 字段已经限定打包范围（`src/`、`tests/`、`public/`、配置与文档）；`node_modules/`、`dist/`、`.env.local` 不会进包。

> **一个 npm 的行为要知道**：`package-lock.json` 不会被 `npm pack` 打进 tarball（npm 的固定行为）。所以接收方 `npm install` 会按 semver 重新解析版本。要连版本都锁死，直接发仓库压缩包（`git archive` / zip），不要用 tarball。

**如果接收方也要演示三窗口**：告诉他们两个无痕窗口必须独立开（Ctrl+Shift+N 两次），不能在同一个无痕窗口里开两个标签页——那样它们共享 IndexedDB，等于同一个人。
